# 项目吃透指南（Student Notes）

> 本文档整理自对项目 `ride-hailing-analytics-system` 的评估，目的是帮助开发者（尤其是面试准备者）从"会跑 demo"到"能吃透、能讲透"这个项目。

---

## 一、现状评估（诚实版）

| 维度 | 评价 | 说明 |
|------|------|------|
| **工程完整度** | 强 | 安全/测试/监控/Docker/前端全有，比绝大多数面试项目扎实 |
| **业务贴合度** | 强（优势） | 卡券核销、异常检测、运营报告都是网约车数据运营的日常 |
| **多 Agent 真实性** | ⚠️ 雷区 | 所谓"协作"本质是固定顺序流水线（SQL→Analysis→Report），Agent 间没有真正并发/协商/冲突解决 |
| **NL2SQL 质量** | ⚠️ 无评测 | 没有评测集，准确率、复杂 join 能力全靠嘴说 |
| **数据真实性** | ⚠️ mock | 数据是 `generate_data.py` 造的，没接真实业务验证 |
| **扩展故事** | 弱 | 单实例，没讲高并发/水平扩展 |

> 注：上表是**设计层面**的诚实评估；实现层面本项目还在真实端到端实测中踩过 6 个具体坑（schema 列名漂移、mock 测试盲区、.env 不同步、多 Agent 名实不符、文档对齐、端口占用），已全部修复并写入 README『踩坑记录与复盘』，对应本指南第六节"面试可能会被追问的坑"。

### 最大的面试雷区

如果说"多 Agent 自主协作"，面试官一问"它们怎么并发？冲突怎么解决？"就容易露馅。**正确说法**：

> "我设计的是 **Orchestrator + 专业化 Agent + 共享黑板（SharedMemory）** 模式，当前按依赖关系顺序编排；相比完全去中心化的多 Agent，这种可控、可调试、确定性强，也更适合数据分析这种有固定 pipeline 的场景。如果要进一步并行，我可以让无依赖的 Agent 用 `asyncio.gather` 并发。"

## 二、如何吃透：四层理解法

不要背代码，按这四层建立"能讲出来"的认知。

### 第 1 层｜架构层（能白板画出）

- 五层：用户层 → 网关(Nginx/CORS) → 应用(FastAPI) → 核心(Query/Agent/Analysis) → 基础设施(DB/缓存/监控)
- 关键文件：`app/main.py`（装配）、`docker-compose.yml`（拓扑）

### 第 2 层｜数据流层（一条查询的生命周期）

```
请求 → 输入校验(validators) → [单Agent] generate_sql→run_sql→interpret→recommend
                          → [多Agent] Orchestrator 建计划 → SQLAgent→AnalysisAgent→ReportAgent(共享黑板)
→ 统一错误处理器 → 返回
```

每个环节的输入/输出/兜底（看 `query.py` 的 try/except 就很清楚）。

### 第 3 层｜模块层（逐个击破）

| 模块 | 路径 | 你要能讲清的 |
|------|------|------|
| NL2SQL | `app/nlsql/` | 怎么把 schema 喂给 LLM、怎么只允许 SELECT（安全） |
| Agent | `app/agent/` | 基类/消息/共享记忆设计、为什么顺序执行 |
| 安全 | `app/security/` | 4 个中间件各自防什么 |
| 历史/导出 | `app/history/` | 为什么用独立 SQLite 存历史 |
| 报告/异常 | `app/report/`、`app/anomaly/` | 这两块直接对应真实工作，重点吃透 |

### 第 4 层｜取舍与改进层（面试加分项）

每个技术选型能答 why / why not：FastAPI 为什么选、为什么自己写 Agent 框架而不直接用 LangChain/AutoGen、SQLite→MySQL 怎么切。

## 三、结合运营背景，最高效的吃法

最大的优势是**这是本职工作的数字化**。把项目模块映射成日常 KPI：

- 仪表盘指标 = 每天盯的核销率/完成率/GMV
- 异常检测阈值（订单降 20%、核销率降 30%）= 真实告警规则的来源
- 运营报告 = 写的周报月报

**用"如果这是我的真实工作，我会怎么改"的视角去读代码**，记忆会非常牢固，面试也能讲出业务 insight 而非纯技术八股。

## 四、自测：达到"吃透"的 3 个标准

1. ✅ 不看书，白板画出架构图 + 一条查询的完整链路
2. ✅ 能现场改一个小功能（比如加一个"按城市下钻"的图表）
3. ✅ 能回答下一节的 5 个高频题

## 五、面试高频自测题

1. 为什么选 FastAPI？同步还是异步？瓶颈在哪？
2. NL2SQL 怎么保证不生成破坏性 SQL？（答：白名单只允许 SELECT + 校验器）
3. 多 Agent 之间怎么通信？为什么是顺序而不是并发？
4. 如果 LLM 生成的 SQL 执行报错，系统怎么兜底？
5. 你怎么**量化**这个系统的效果？（建议补一个 10~20 条问题的评测集，算准确率）

## 六、面试可能会被追问的坑（及标准回答）

> 来源：本项目在真实端到端实测中踩过的 6 个具体坑（已全部修复，完整记录在 README『踩坑记录与复盘』）。面试官最爱从"你以为没问题"的地方追问，准备好就能把危机变加分项——**核心是诚实 + 有闭环 + 有复盘**。

### 坑 1：Schema 列名漂移（最致命，曾让核心功能全挂）
- **面试官可能问**："你项目真能跑吗？44 个测试都过了为什么还会出 bug？"
- **标准回答**：能跑，但这个过程恰恰暴露了问题。早期建库时把 `orders.order_date` 规范成 `order_time`、`amount`→`order_amount`，但 4 处业务代码（数据生成 / 异常检测 / 报告 / 仪表盘）还引用旧列名，且彼此没同步，结果服务能启动、单测全绿，真实一跑 4 个模块全报 `no such column`。
- **体现的成长**：① 改 schema 必须全局检索所有引用点（代码 + 脚本 + 测试），不能只改建表语句；② 单测全 mock 数据库会掩盖 schema 契约问题，**必须有一次真实 DB 的端到端集成测试**才能证明系统真能跑。

### 坑 2：44 测试全绿 ≠ 系统可用（mock 测试的盲区）
- **面试官可能问**："你的测试覆盖率高吗？这些测试能信吗？"
- **标准回答**：测试数量够（44 个），但全部用 mock 把数据库层替换掉了，没有一条用例真正连 SQLite 执行过建表 / 插入 / 查询。逻辑对不对能验证，集成通不通验证不了。我后来补了冒烟测试（真实灌库后逐个 curl 核心接口），并建议保留少量内存 SQLite 集成测试。这体现的是对**测试金字塔**的理解。
- **加分话术**："mock 测逻辑，集成测契约，两者不可互相替代。"

### 坑 3：.env 不进版本库，跨机器配置丢失
- **面试官可能问**："你怎么做密钥管理？部署到一台新机器第一步做什么？"
- **标准回答**：`.env` 被 `.gitignore` 忽略（这是正确的，避免泄露密钥），所以不会随仓库同步。每台机器首次拉取后必须 `cp .env.example .env` 填 `LLM_API_KEY`。无 key 时服务仍能启动、非 LLM 功能（仪表盘 / 异常 / 监控）可用，缺 key 的接口会优雅返回 500——这是预期降级，不是 bug。
- **体现**：有安全意识 + 明确的部署 runbook。

### 坑 4："多 Agent 协作"早期名实不符（最重要的人设雷区）
- **面试官可能问**："这几个 Agent 怎么通信？怎么并发？冲突怎么解决？"
- **标准回答**（详见上文"最大的面试雷区"）：早期 v0.1~v0.4 确实是固定顺序流水线（Planner→SQL→Analysis→Report），v0.5.0 才真正落地 Orchestrator + 3 个专业化 Agent + 共享黑板（SharedMemory）。我建议**如实说明演进**，不要硬说"完全去中心化多 Agent"——面试官一追问并发 / 冲突就容易露馅。现在的说法是"可控、可调试、确定性强，适合数据分析 pipeline；无依赖的 Agent 可用 `asyncio.gather` 并发"。
- **体现**：技术叙事与架构一致，不夸大。

### 坑 5：README 表格在终端 / 部分渲染器错位
- **面试官可能问**：（一般不会直接问，但会看文档）"你的文档这么细，细节也管？"
- **标准回答**：版本对比表最早用 Markdown 表格 + ✅/❌ emoji，在 CJK + emoji 混排下因字符宽度不一经常对不齐。我改成等宽代码块 + 固定宽度 `✓`/`✗` 符号，保证任何渲染器对齐。
- **体现**：把文档当产品，对渲染细节敏感（这是工程素养的侧面信号）。

### 坑 6：旧进程占用端口，误测到旧代码
- **面试官可能问**："你怎么保证你测的就是最新代码？"
- **标准回答**：有一次实测时端口 8001 被更早启动的旧 uvicorn 实例接管，curl 打到的其实是旧代码，一度误以为修复没生效。后来养成习惯：验证修复前先 `netstat -ano | findstr :8001` 查端口占用、强杀残留进程，再重启最新代码复验。
- **体现**：工程严谨，知道"环境干净"是测试可信的前提。

### 怎么讲这几个坑（总原则）
1. **不回避**：主动说"我们实测时真踩过 X"，比被问住强 10 倍。
2. **有闭环**：每个坑都带上"怎么发现的 → 怎么修的 → 以后怎么避免"。
3. **拔高**：把坑升华成方法论（测试金字塔、schema 治理、密钥管理、文档即产品）。
4. **关联业务**：坑 1 / 2 正好印证你是"会真跑、真测"的工程师，区别于只写 demo 的人。
